# AutoHotkey v2 C++ Interpreter Documentation

## 1) Executive Summary

This repository contains the C++ implementation of the AutoHotkey v2 interpreter. Its primary purpose is to parse, interpret, and execute AutoHotkey v2 scripts, translating AHK commands and directives into corresponding Windows API (WinAPI) calls and internal logic to automate various tasks on the Windows operating system. This includes handling user input (keyboard and mouse), managing windows, interacting with the clipboard, and controlling processes. The application is built using MSBuild and targets Windows platforms.

The high-level architecture consists of several key components: a core application module responsible for initialization and the main message loop, a script parsing and execution engine, modules for interacting with the Windows GUI (windows, controls, messages), input handling (hooks, simulation), and various utility modules for file I/O, process management, and COM interactions. These components collaborate by maintaining a global application state and dispatching WinAPI calls based on the interpreted AHK script logic.

This document covers the C++ code only and does not include any AHK v2 scripts.

### Layering Model

The AutoHotkey v2 interpreter generally follows a layered architecture, though with some cross-cutting concerns due to its nature as a system-level automation tool.

1.  **Infrastructure Layer:** This is the lowest layer, directly interacting with the Windows API. Modules like `keyboard_mouse.cpp`, `window.cpp`, `clipboard.cpp`, `lib/file.cpp`, `lib/process.cpp`, `script_registry.cpp`, and `script_com.cpp` primarily reside here. They encapsulate direct WinAPI calls and provide a slightly higher-level interface for the layers above. The `globaldata` module also sits at this layer, providing fundamental shared state.
2.  **Domain Layer:** This layer contains the core logic for interpreting AHK v2 semantics and managing the application's internal state. The `script.cpp` module, which handles script parsing, execution, and managing hotkeys/hotstrings, is central here. `hotkey.cpp` and `input_object.cpp` also belong to this layer, defining the internal representation and behavior of AHK-specific constructs.
3.  **Application Layer:** This layer orchestrates the overall application flow, managing the main message loop, handling command-line arguments, and coordinating between the domain and infrastructure layers. `AutoHotkey.cpp` (the main entry point) and `application.cpp` (for general application utilities and timers) are key components in this layer.
4.  **Presentation Layer:** While AutoHotkey is primarily a backend automation tool, it does have minimal UI elements for user interaction (e.g., `MsgBox`, tray icon, GUI commands). The `window.cpp` module, particularly its `CreateWindows` function and `MsgBox` implementation, touches upon this layer, as do the `script_gui.cpp` and `lib/Gui.*.cpp` files for AHK's GUI commands.

Cross-cutting concerns like error handling (`error.cpp`), debugging (`Debugger.cpp`), and string conversion (`StringConv.cpp`) interact across multiple layers.

### Data Flow

The data flow within the AutoHotkey v2 interpreter can be summarized as follows:

1.  **Input/Configuration:**
    *   **Command-line Arguments:** `_tWinMain` receives `lpCmdLine`. `ParseCmdLineArgs` in `AutoHotkey.cpp` parses these arguments (`__targv`), identifying special switches (e.g., `/restart`, `/force`, `/ErrorStdOut`, `/include`, `/validate`, `/Debug`) and the primary script file path. Remaining arguments are stored in the `A_Args` array, accessible by the script.
    *   **Script File:** The `script_filespec` (either from command-line or embedded resource `SCRIPT_RESOURCE_SPEC`) is passed to `g_script.LoadFromFile()`. This function reads the AHK v2 script content.
    *   **Internal Configuration:** Global variables in `globaldata.h` (e.g., `g_AllowOnlyOneInstance`, `g_MaxHistoryKeys`, `g_HSPriority`, `g_DefaultScriptCodepage`) are initialized during `EarlyAppInit` and `g_script.Init()`, often based on defaults or command-line overrides.

2.  **Internal Models:**
    *   **Script Object (`g_script`):** The `Script` class (in `script.h`/`.cpp`) holds the parsed representation of the AHK script, including its code, hotkeys, hotstrings, functions, and variables.
    *   **Hotkey/Hotstring Objects:** Parsed hotkeys and hotstrings are stored as `HotkeyCriterion` objects (in `hotkey.h`) linked in global lists (`g_FirstHotCriterion`, `g_LastHotCriterion`).
    *   **Global State:** `globaldata.h` defines numerous global variables (`g_hInstance`, `g_KeybdHook`, `g_PhysicalKeyState`, `g_WorkingDir`, etc.) that maintain the application's runtime state, including keyboard/mouse states, hook handles, and various settings.
    *   **Object Model:** `Object::CreateRootPrototypes()` initializes the AHK object model, providing the foundation for script-level objects and arrays.

3.  **Execution Pipeline:**
    *   **Initialization:** `EarlyAppInit` performs critical early setup (e.g., `SetErrorMode`, `UpdateWorkingDir`, `global_init`, `Object::CreateRootPrototypes`).
    *   **Instance Check:** `CheckPriorInstance` handles single-instance logic, potentially communicating with or terminating a previous instance using `FindWindow` and `PostMessage`.
    *   **Runtime Setup:** `InitForExecution` creates the main application windows (`g_script.CreateWindows()`) and initializes key history buffers.
    *   **Debugger (Optional):** If `/Debug` is specified, `g_Debugger.Connect()` attempts to establish a debug session.
    *   **Hotkey/Hook Activation:** `Hotkey::ManifestAllHotkeysHotstringsHooks()` activates all defined hotkeys, hotstrings, and installs necessary low-level keyboard/mouse hooks (`SetWindowsHookEx`).
    *   **Auto-Execute Section:** `g_script.AutoExecSection()` executes the initial part of the AHK script. This is where the script's main logic begins.
    *   **Main Event Loop:** If the script is persistent (`g_script.IsPersistent()`), `MsgSleep(SLEEP_INTERVAL, WAIT_FOR_MESSAGES)` enters the main message loop, continuously processing Windows messages (`GetMessage`, `DispatchMessage`) and script timers. This loop is the heart of the interpreter, allowing it to react to user input, system events, and script-defined timers.
    *   **AHK Command Execution:** Within the script's execution, AHK commands (e.g., `Send`, `Click`, `WinActivate`, `RegRead`) are translated into calls to internal C++ functions, which in turn make the appropriate WinAPI calls (e.g., `SendInput`, `SetCursorPos`, `SetForegroundWindow`, `RegQueryValueEx`).

4.  **Output/Write Path:**
    *   **WinAPI Interactions:** The primary "output" of the C++ program is its interaction with the Windows operating system via WinAPI calls, which perform the automation tasks defined by the AHK script.
