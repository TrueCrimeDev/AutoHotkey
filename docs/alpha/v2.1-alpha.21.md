# AutoHotkey v2.1-alpha.21

**Released:** 2026-03-08
**Previous:** [v2.1-alpha.20](./v2.1-alpha.20.md)
**Next:** [v2.1-alpha.22](./v2.1-alpha.22.md)
**Upstream tag:** [`v2.1-alpha.21`](https://github.com/AutoHotkey/AutoHotkey/tree/v2.1-alpha.21)

## Overview

This release is entirely focused on the module system introduced in earlier alpha versions. The `#Module` and `#Import` directives receive a significant round of refinements: module name scoping becomes file-local, module lifetimes are now bounded by the file that declared them, initialization order is driven by first-reference rather than declaration order, and the `#Import` directive gains a `"file:module"` syntax for targeting named sub-modules inside a file. Several error-detection gaps are also closed, and the `!~=` not-RegExMatch operator spelling is finalised.

## New features

### `#Import "file:module"` — target a named sub-module

When a file defines multiple `#Module` sections, you can now import a specific named sub-module directly by appending a colon and the module name to the file path:

```autohotkey
; shapes.ahk defines:
;   #Module Circle
;   #Module Rectangle

#Import "shapes.ahk:Circle"          ; imports the Circle module as "Circle"
#Import "shapes.ahk:Rectangle" as R  ; imports Rectangle, aliased to R
```

The file path before the colon follows the same resolution rules as a plain `#Import "file.ahk"`. The module name after the colon must match a `#Module` directive inside that file. An error is raised if the named module is not found after the file is loaded.

The special empty-path form (`#Import ":ModName"`) imports a named module from the current file's own scope.

---

### Module initialization triggered on first reference

Modules are no longer initialized strictly in declaration order. Instead, when a name imported from a module is first read, the engine automatically executes that module's initialization code if it has not yet run. This means the order in which `#Import` directives appear in the script no longer determines the order modules initialize — the order of actual use does.

```autohotkey
; ModA.ahk
#Module ModA
global Value := ComputeValue()
ComputeValue() => 42

; main.ahk
#Import ModA
MsgBox(ModA.Value)   ; ModA initializes here, on first reference
```

This works for both direct module-object references and individual imported names. If a module's initialization fails, the error is reported at the point of first use.

---

### `#Module __Init` — reopen the initial module of a file import

Inside a file that defines named modules via `#Module`, you can now write `#Module __Init` to return to (reopen) the file's initial implicit module — the code that runs before any named `#Module` directive appears. This allows shared setup code to be placed at the top of the file and then returned to after defining named modules.

```autohotkey
; lib.ahk
global SharedCounter := 0    ; part of __Init

#Module FeatureA
global A_Value := "alpha"

#Module __Init               ; back to the file's initial module
global SharedCounter += 1    ; __Init code continues here
```

## Changes

### `#Module` names are now private to each file-based module

Previously, `#Module` names were registered in a global list, which meant a name used in one included file could conflict with or shadow a module of the same name in another file. Names are now scoped to the file that contains the directive — `FindDirectiveModule` only searches the chain of modules that belong to the current file's own scope when resolving a `#Module` directive reference. The special names `AHK` and `__Main` remain globally accessible.

This also means that two different included files can each define a `#Module Util` without conflicting with each other.

---

### `#Module` ends at the end of the file containing it

A `#Module` block's scope is now automatically closed when the parser finishes reading the file in which the `#Module` directive appeared. Code in a file that `#Include`s a module-containing file is no longer implicitly inside the last module opened by that include. The parser walks up the module chain and reopens the appropriate outer module when a file finishes loading.

Before this change, a module opened inside an included file could inadvertently remain the "current module" while the including file continued to be parsed.

---

### `#Module` now requires a valid identifier

Passing a name that does not satisfy AHK's identifier rules now produces a load-time error: `Invalid module name`. Previously the name was accepted without validation, which could lead to confusing behaviour at import-resolution time. The same `ValidateName` logic used for variables, functions, and classes is now applied to module names.

```autohotkey
#Module 123bad   ; Error: Invalid module name
#Module My-Mod   ; Error: Invalid module name (hyphens not allowed)
#Module MyMod    ; OK
```

---

### `#Import` is now a directive only — `Import` statement removed

The `Import` statement (i.e., `Import ModName` as a regular expression statement on its own line, without the `#` prefix) has been removed. `#Import` as a directive (with the `#` prefix) remains the correct and only form. Using `#Import` inside a function body, class definition, or other nested context is now an explicit error.

```autohotkey
; REMOVED — no longer valid:
; Import SomeModule

; Correct form (top-level only):
#Import SomeModule
```

---

### Module initialization order: first `#Module` reference wins

Previously, when multiple modules each referenced one another, the initialization sequence could be ambiguous. The engine now records the first-reference point for each module and uses that to drive execution order. Internally, import variables carry a deferred-initialization flag so that the module's code runs exactly once on the first read, regardless of where the `#Import` appears relative to the imported module's definition.

---

### `!~=` is now the not-RegExMatch operator (was `~!=`)

The negated RegExMatch infix operator has been re-spelled from `~!=` to `!~=`. The `!` (logical-not) now comes first, which is consistent with how other negated operators read in AHK v2 (`!=`, `!==`). The old `~!=` spelling is no longer recognised.

```autohotkey
haystack := "Hello World"
pattern  := "i)^hello"

if (haystack ~= pattern)
    MsgBox("Matched")

if (haystack !~= pattern)          ; v2.1-alpha.21+
    MsgBox("Did not match")

; Old spelling no longer works:
; if (haystack ~!= pattern) ...    ; Error
```

The operator still compiles to a `RegExMatch()` call internally; the `!` is applied to the result.

---

## Breaking changes

### `~!=` no longer recognized as the not-RegExMatch operator

Any script that used `~!=` must be updated to `!~=`. This is a simple search-and-replace.

---

### `Import` statement removed

Scripts that used bare `Import ModName` (without the `#` prefix) will fail to load. Replace each occurrence with `#Import ModName` at the top level of the file.

---

## Bug fixes

- **`#Import` forward-reference fix**: Names imported from a module are now correctly resolved even when the `#Import` directive appears before the declarations in the target module. Previously, if the importing module's `#Import` was processed before the exported names were declared, resolution silently failed.
- **`#Import` accepts undeclared globals**: When importing specific names (`#Import "file" {Name}`), the resolver now creates a placeholder variable for names that do not yet exist in the target module's variable list. This handles both forward references and global variables that are assigned but not explicitly declared with `global`.
- **Duplicate `#Include` with `#Module` now raises an error**: If the same file is `#Include`d more than once and that file contains a `#Module` directive, the engine now detects the duplicate and reports `#Module in duplicate #Include` rather than silently re-entering the module.
- **Hotkey followed by `#Module` now raises an error**: A pending hotkey definition followed immediately by `#Module` (without a separator) is now correctly flagged as `ERR_UNEXPECTED_DIRECTIVE`.
- **Duplicate module loading fixed**: Importing the same file-based module from multiple places no longer causes the module's code to be loaded and initialized more than once.

## Internal / build / parser changes

- `OpenNewModule()` renamed to `CreateModule()` to distinguish initial creation from reopening an existing module (`ReopenModule()`).
- `ParseImportStatement()` (which handled both directive and statement forms) replaced by the directive-only `ParseImportDirective()`.
- `ScriptImport` struct gains a `mod_path` field separate from `mod_name` to support the `"file:module"` split.
- `Var::InitializeConstant()` generalised to `Var::SelfInitialize()`, which handles both class static initializers and module initialization-on-first-reference. Import variables now use the `VAR_ALIAS | VAR_ATTRIB_UNINITIALIZED` combination to signal deferred module initialization.
- `Var::SetImport()` introduced to atomically configure an import variable's alias, module pointer, and uninitialized flag.
- `ScriptModule::IsFileModule()` predicate introduced (`mSelfFileIndex != ABSOLUTE_MAX_SOURCE_FILES`).
- `FindDirectiveModule()` introduced: searches only the directive-visible chain (stopping at file module boundaries) rather than the global `mModules` list.
- `DISPLAY_MODULE_ERROR` constant added so that `ValidateName` can report "Invalid module name" specifically.
