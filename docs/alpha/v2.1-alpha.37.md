# AutoHotkey v2.1-alpha.37

**Released:** 2026-10-25 (forum announcement)
**Previous:** [v2.1-alpha.36](./v2.1-alpha.36.md)
**Upstream commit:** [`279247ee`](https://github.com/AutoHotkey/AutoHotkey/commit/279247ee)

> Latest release in the v2.1-alpha series as of 2026-10-25. Merged into this fork on
> 2026-10-25 (branch `m1/upstream-alpha37`).

## Overview

Alpha.37 is a DllCall and Struct release: `unset` is a null pointer for `Str`
and pointer parameters, a numeric struct instance passes its value, structs
gain `__New(fieldValues*)`, `Struct.At` accepts `Struct` itself, and `IsSet`
accepts a property or call without a written `?`. Five crashes or
undefined-behaviour cases are closed. Fifteen upstream commits after
`0b8e6fa3`, including a `v2.0` merge (`279247ee`).

## Changed

### `DllCall`/`ComCall` `Str`, `*` and `P` parameters accept `unset` as null

(`1fa8d1f1`) `DllCall("f", "Str", unset)` and `DllCall("f", "Int*", unset)`
pass a null pointer. This differs from `"Int*", &v := unset`, which passes the
address of a variable. Before, both threw "Missing a required parameter."

```autohotkey
size := DllCall("GetCurrentDirectoryW", "UInt", 0, "Str", unset, "UInt")  ; buffer size query
DllCall("msvcrt\_wcsdup", "Str", unset, "Ptr")   ; 0: _wcsdup(NULL)
```

### `IsSet(a.b)` implies a final `?`

(`42fb8260`) `IsSet(o.prop)` and `IsSet(f())` are permitted and mean
`IsSet(o.prop?)` / `IsSet(f()?)`: 0 when the property is missing or the call
returns unset. Only the final access is optional, so `IsSet(o.x.y)` with no
`o.x` still throws `PropertyError` at run time. Before, both forms were a load
error, "IsSet requires a variable or unset expression."

### `Struct.At` accepts `Struct` itself

(`d99ace41`) `Struct.At(ptr)` returns a zero-field `Struct` view (`Ptr` is the
address, `Size` is 0) instead of throwing "Invalid class". A subclass is no
longer required.

### `DllCall(..., Int32, n, ...)` passes a numeric struct's value

(`91ab8b82`) With a numeric class as the type and an instance of it as the
argument, `DllCall` passes the instance's value, not its address; the same
for `Int64` and the other numeric classes. `DllCall("msvcrt\abs", Int32, n,
"Int")` with `n.__Value := -5` returns 5. Before, `Int32` threw `TypeError`
"Expected a Number but got an Int32." and `Int64` corrupted memory.

## New

### `Struct.Prototype.__New(fieldValues*)`

(`176a9d1d`) Calling a struct class with arguments assigns each field in
declaration order. The count must equal the field count (`Pt(3)` on a
two-field struct throws "Invalid number of parameters."); no arguments still
zero-initializes. A script-defined `__New` can delegate with
`super.__New(...)`, which threw `MethodError` before.

```autohotkey
struct Pt {
    x : Int32
    y : Int32
}
p := Pt(3, 4)          ; p.x = 3, p.y = 4
```

## Fixes

- Typed callback parameters of an array subtype (`c20d449d`): `CallbackCreate`
  recognizes an array struct type and passes it by pointer (`MdType::Array`),
  and an array type is rejected as the return type. The fork could not drive
  this from script: an array class such as `Int32[2]` is only reachable as a
  field type, and `ObjGetBase` on a field value yields its prototype, which
  `CallbackCreate` rejects. Unverified here.
- `a.b()` throws `UnsetError` "No value was returned." when `a.b => unset`
  (`2f4f3967`); it exited 11 "Invalid memory read/write." before.
- `a.b[c]` throws `PropertyError` (`Func` has no `__Item`) when `a.b` is a
  method (`77595540`); it returned without throwing before.
- `NumGet`/`NumPut` throw `ValueError` "Invalid parameter(s)." when the type is
  not a numeric class or type string: an empty string, a plain object, or a
  `Struct` class with fields (`2cdf79a6`). Before, all three read or wrote
  memory as a pointer-sized integer (the default `num_size` was
  `sizeof(DWORD_PTR)`; it is now 0 and reaches the existing invalid-parameter
  check). This is the second of the three engine findings Copilot raised on
  fork PR #32.
- `DllCall(..., IntPtr, obj, ...)` with a plain object throws `TypeError`
  "Expected a Number but got an Object." (`f74fd031`); it exited 11 before.
- `#Import A {invalid}` no longer trips an assertion in debug builds
  (`348ae41b`); release builds were unaffected.
- Debugger: a breakpoint on a line group whose first line is detached no
  longer dereferences null (`d4522806`). Not exercised here.
- From `v2.0` (`43e233e7`): `a & b::AltTabMenu` no longer crashes in the
  keyboard hook. Not exercised here.
