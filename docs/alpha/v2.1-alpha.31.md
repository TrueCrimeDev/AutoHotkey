# AutoHotkey v2.1-alpha.31

**Released:** 2026-08-28
**Previous:** [v2.1-alpha.30](./v2.1-alpha.30.md)
**Upstream tag:** [`v2.1-alpha.31`](https://github.com/AutoHotkey/AutoHotkey/tree/v2.1-alpha.31)

> Latest release in the v2.1-alpha series as of 2026-09-08.

## Overview

Alpha.31 is a module-system release. Its headline change reverses the export model that
alpha.11 through alpha.30 built up: the `export` keyword is gone, and every name defined
inside a `#Module` section is exported implicitly. Imported names stay private to the
importing module unless re-exported with `#Import Export`, and names beginning with `_`
are skipped by wildcard imports, which gives modules a lightweight "private by convention"
mechanism.

Around that change sit a fix for `#Import` inside `#Module AHK`, a cluster of unset/blank
semantics fixes (output parameters, `RegExMatch`, multi-level imports, `Props(v)`, error
markers), two Struct/reference fixes (boxed nested-struct destructor crash, `a := b` from a
virtual reference), two `GuiCtrl.OnMessage` threading fixes, and the v2.0.27 fixes that
arrived through the v2.0 merge.

If any of your modules use `export` in front of a function, class or `global`
declaration, **they will no longer load on alpha.31**. See Breaking changes for the exact
failure modes and the (mechanical) migration.

## Changes

### `export` is now implied for names defined in a module

Since alpha.11 (`Added Export.`, `04b7f2e6`) the module system worked on an opt-in model: a
name defined inside a `#Module` section was private unless prefixed with `export`
(`export Fn() {}`, `export class C {}`, and — for variables, since alpha.20 —
`export global x := 1`, a form alpha.20 chose so that a user function called `Export()`
would keep working). Alpha.22 then tightened the grammar so that `export a() => b` parsed
as a call to `export()`, and alpha.25 patched a conflict between `global g` in a function
and a prior `export global g`.

Alpha.31 reverts all of that. The three commits that added and extended the keyword
(`04b7f2e6` alpha.11, `c5d738e9` alpha.20, `2f16bcbc` alpha.25) are reverted by
`52caabbc`, `10c1da5a` and `d7b9469a` respectively, and a follow-up commit flips the
default: **every function, class, `global` declaration and top-level assignment inside a
module is exported.** The only names that are *not* exported are those the module itself
imported.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module Geometry

global Pi := 3.14159265358979      ; exported — no keyword needed
CircleArea(r) => Pi * r ** 2       ; exported
class Point {                      ; exported
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Scale := 2                         ; plain top-level assignment — also exported

#Module __Main
#Import Geometry {*}

MsgBox(Round(CircleArea(2), 3))    ; => 12.566
MsgBox(Point(3, 4).y)              ; => 4
MsgBox(Scale)                      ; => 2
MsgBox(Geometry.Pi)                ; => 3.14159265358979  (module object access, unchanged)
```

On alpha.30 the same script loads with warnings (*This global variable appears to never be
assigned a value: CircleArea / Point / Scale*) and dies at run time with *This global
variable has not been assigned a value. Specifically: CircleArea* (exit 10), because nothing
was exported. The module object form (`Geometry.Pi`) has been able to read any module global
since alpha.20 and is unaffected.

Internally `VAR_EXPORTED` became `VAR_IMPORTED` with the meaning inverted: `IsExported()`
is now `!(mScope & VAR_IMPORTED)`. Built-in variables, built-in functions and class
variables no longer carry an export flag at all.

### Names beginning with `_` are skipped by wildcard imports

Because every name is exported, the engine needs another way to keep helpers out of an
importer's namespace. `ScriptModule::FindImportedVar` — the lookup behind `{*}` — now
returns nothing for any name whose first character is `_`. Such names are still exported:
they can be imported by name, and they are reachable through the module object.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module Geometry
_Helper() => "reachable"
Area(r) => 3 * r * r

#Module __Main
#Import Geometry {*}
MsgBox(Area(2))                                  ; => 12
MsgBox(IsSet(_Helper) ? "imported" : "skipped")  ; => skipped
MsgBox(Geometry._Helper())                       ; => reachable
```

Explicit import still works:

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module Geometry
_Helper() => "reachable"

#Module __Main
#Import Geometry {_Helper}
MsgBox(_Helper())    ; => reachable
```

The rule applies to wildcard *re-exports* (`#Import Export X {*}`) as well, since they use
the same lookup.

### Imported names are still private unless re-exported

The changelog's qualifier — *"imported names are still not exported by default"* — is the
half of the old model that survives. When module `Facade` imports `Core`, `Core`'s names
become part of `Facade`'s namespace but are flagged `VAR_IMPORTED`, so a module that
imports `Facade` does not see them:

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module Core
Greet(name) => "hi " name

#Module Facade
#Import Core {*}                     ; private to Facade
Shout(name) => StrUpper(Greet(name))

#Module __Main
#Import Facade {*}
MsgBox(Shout("bob"))                             ; => HI BOB
MsgBox(IsSet(Greet) ? "visible" : "not visible") ; => not visible
```

To forward them, use the pre-existing `#Import Export` form (alpha.17 for named
re-exports, alpha.24 for `{*}`):

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module Core
Greet(name) => "hi " name

#Module Facade
#Import Export Core {*}              ; re-export Core's names
Shout(name) => StrUpper(Greet(name))

#Module __Main
#Import Facade {*}
MsgBox(Shout("bob"))   ; => HI BOB
MsgBox(Greet("ann"))   ; => hi ann
```

`#Import Export` is the only place the word `Export` still has meaning. As a plain
identifier it is free again: a user function named `Export()` loads and runs.

## Breaking changes

### The `export` keyword no longer parses

`export` was removed from the action table (`ACT_EXPORT`) and from the function/class
definition scanners, so it is now an ordinary identifier. What happens to existing code
depends on which declaration form it was attached to. All three were observed on the
alpha.31 engine:

| Declaration | Result on alpha.31 | Exit |
|-------------|--------------------|------|
| `export Fn(x) {` … `}` | Loads with a warning *"This global variable appears to never be assigned a value: export"*, then dies at that line at run time with *"This global variable has not been assigned a value. Specifically: export"* | 10 |
| `export global X := 1` | Load error: *The following reserved word must not be used as a variable name: "global"* | 12 |
| `export class K {` … `}` | Load error: *Unexpected "{"* | 12 |

The function form is the sneaky one: it does not fail at load. The line is parsed as an
expression statement beginning with a variable named `export`, so the module loads (with a
warning if `#Warn` is on) and fails only when execution reaches it.

**Migration:** delete the keyword. Nothing else changes — the name was going to be exported
anyway.

```autohotkey
; Before (alpha.20 – alpha.30):
; export global Limit := 10
; export Twice(x) {
;     return x * 2
; }
; export class Counter {
; }

; After (alpha.31):
#Requires AutoHotkey v2.1-alpha.31
#Module M
global Limit := 10
Twice(x) {
    return x * 2
}
class Counter {
}

#Module __Main
#Import M {*}
MsgBox(Twice(Limit))   ; => 20
MsgBox(Type(Counter))  ; => Class
```

If a module relied on *not* exporting a helper, rename it with a leading underscore (kept
out of `{*}` imports) or move it into a function scope. There is no other way to hide a
module-level name on alpha.31.

Also gone with the reverts: the `export default` form and `ScriptModule::mSelf` that backed
it. No earlier alpha documentation in this series described `export default`, so no
migration note is given beyond "it does not exist".

## Bug fixes

### Module system

#### `#Import` inside `#Module AHK`

`#Module AHK` reopens the *built-in* module — the namespace every other module falls back
to when a name is not found locally or via an import. Functions and classes defined in an
`#Module AHK` section therefore behave like built-ins: they are visible from every module
without `#Import`, and the section's top-level code runs before any other module.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module AHK
Twice(x) => x * 2

#Module Other
Quad(x) => Twice(Twice(x))       ; Twice resolves without an import

#Module __Main
#Import Other {*}
MsgBox(Quad(3))                  ; => 12
```

What was broken: the built-in module was not part of the module list while imports were
resolved, so any `#Import` directive written inside `#Module AHK` was silently never
resolved. The directive loaded, the names it should have brought in stayed unset, and the
script failed at run time with *"This local variable has not been assigned a value"*
(observed on alpha.30). `Script::LoadFromFile` now links the default module to the built-in
module before `ResolveImports()` runs (and unlinks it afterwards so the list cannot become
circular), which puts the built-in module's imports on the resolution path.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module AHK
#Import "lib\Helpers.ahk" {*}    ; Helpers.ahk defines Twice(x) => x * 2
Quad(x) => Twice(Twice(x))       ; visible to every module, no import needed

#Module __Main
MsgBox(Quad(3))                  ; => 12   (alpha.30: run-time error, Twice unset)
```

The second half of the fix is in `FindModuleFileIndex`: an import of the form
`#Import ":Name"` (a sub-module of *the current file*) now reports *"Module not found"*
from inside `#Module AHK`, because the built-in module has no source file. Previously the
empty-name path returned `OK` with `aFileIndex == ABSOLUTE_MAX_SOURCE_FILES` (the built-in
module has no source file); on alpha.30 this was moot because imports in `#Module AHK` were
never resolved (the directive loaded and the names stayed unset). It now returns
`CONDITION_FALSE`, so the directive reports *Module not found*. Note that in-file
`#Module` sections are not reachable from `#Module AHK` by bare name either
(*"Module not found"* on alpha.31); only file modules can be imported there.

#### Multi-level import turned `unset` into `""`

When a name is imported through two hops (`Base` → `Mid` → main), the importer's variable
is an alias of an alias. `ExpandExpression` decided whether to push the value or treat it
as unset by asking only the *first* level (`IsUninitializedAliasFor`), so an unset variable
two hops away came through as an empty string. `Var::SelfInitialize` now flattens the alias
chain and the check uses plain `IsUninitialized()`.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
#Module Base
global Cfg                 ; declared, never assigned

#Module Mid
#Import Export Base {Cfg}  ; first hop

#Module __Main
#Import Mid {Cfg}          ; second hop
MsgBox(IsSet(Cfg))         ; => 0
MsgBox(Cfg ?? "<unset>")   ; => <unset>   (alpha.30: "" — ?? saw an empty string)
```

On alpha.30 `IsSet(Cfg)` was already `0`, but the `??` expression produced `""` — the
mismatch this fix removes.

### Unset / blank semantics

#### Output parameters are "made blank" again, not unset

Built-in functions whose output parameters are typed as `Variant` — `CaretGetPos`
(`&X` / `&Y`), `FileGetShortcut` (`&OutIconNum`), `ImageSearch`, `MouseGetPos`
(`&OutputVarWin` / `&OutputVarControl`), `PixelSearch`, `Run` (`&OutputVarPID`) — could
leave the variable **unset** when the implementation stored nothing, e.g. `PixelSearch` on
no match. The documentation for these functions says the variables are *made blank*, and
that is what v2.0 does. `MdFunc::Call` now converts a missing output value to `""` before
assigning, in both v2.0 and v2.1 mode. (`CaretGetPos` and `FileGetShortcut` already assign
`""` explicitly on their no-value paths, so they share the code path but show no observable
change: `IsSet` is 1 on alpha.30 and alpha.31 alike.)

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
found := PixelSearch(&px, &py, 0, 0, 0, 0, 0x123456)   ; 1x1 region, colour almost certainly absent
MsgBox(found)          ; => 0
MsgBox(IsSet(px))      ; => 1   (alpha.30: 0 — px was left unset)
MsgBox("[" px "]")     ; => []
```

#### `RegExMatch` output variable is unset on no match (v2.1 mode)

The first version of the output-parameter fix (`7dbdf233`, 15 Aug) blanked *all* missing
output values, which also blanked `RegExMatch`'s `&OutputVar` on no match — undoing the
alpha.29 behaviour where it is left unset in v2.1 mode. `9a8b1514` (release day) moved the
blanking to the `Variant` path only. The net effect for anyone upgrading from alpha.30 is
**no change**: the alpha.30 engine already leaves the variable unset.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
RegExMatch("hello", "x", &miss)
RegExMatch("hello", "l+", &hit)
MsgBox(IsSet(miss))    ; => 0
MsgBox(hit[0])         ; => ll
```

The v2.1 behaviour depends on `#Requires AutoHotkey v2.1-alpha.xx` (or the equivalent
module setting); a script without it runs in v2.0 mode and gets `""`.

#### `Props(v)` copies the value of `v` instead of aliasing it

`Props(v)` returns an enumerator over the properties of `v` (or of its base, for a
primitive). The enumerator stored the *variable* `v`, so a getter evaluated during
enumeration saw whatever `v` held at that moment, and a string that had since been freed
could be read after free. The enumerator now takes its own copy of the value (`Object::PropEnum`
gained an `mMemToFree` member for the string case).

The difference is observable once `String.Prototype` has a computed property. Primitive
prototypes do not inherit `DefineProp`, so borrow it from `Object.Prototype`:

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
Object.Prototype.DefineProp.Call(String.Prototype, "Len", {get: (this) => StrLen(this)})

v := "hello"
e := Props(v)          ; enumerator keeps a copy of v's value
v := "hi"
for name, val in e
    MsgBox(name "=" val)   ; => Len=5   (alpha.30: Len=2 — the enumerator aliased v)
```

#### Trailing character in the "unset return" error message

When a call made through a dynamic member name returns unset, the error's `Extra` text
pointed one character too far back into the expression. `f.%'C'%all()` reported
*"Specifically: l()"*; it now reports `()`. The intended `%()` marker for the fully dynamic
form `f.%'Call'%()` is unchanged. (`error_reporting_marker` now backs up over the closing
`%` only when there is one.)

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
f() => unset
try
    r := f.%'C'%all()
catch as e
    MsgBox(e.Extra)    ; => ()     (alpha.30: l())
try
    r := f.%'Call'%()
catch as e
    MsgBox(e.Extra)    ; => %()    (unchanged, intended)
```

### Struct / references

#### Crash destructing a boxed pointer with a nested struct

A `StructClass.At(ptr)` / `StructClass.Ptr` instance ("boxed pointer") does not construct
the nested `Object` headers that an inline struct instance would have. `Object::~Object`
walked those nested slots regardless and called `~Object()` on zeroed memory. The
destructor now checks that the slot's vtable pointer is non-null before destructing it.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
Struct Inner {
    a: Int32
}
Struct Outer {
    items: Inner[3]        ; nested struct array
    b: Int32
}
buf := Buffer(64, 0)
p := Outer.At(buf.Ptr)     ; boxed pointer into buf
p.items[2].a := 5
MsgBox(p.items[2].a)       ; => 5
p := ""                    ; destruct the boxed pointer
MsgBox("released")         ; => released
```

On alpha.30 the `p := ""` line dies with *"Invalid memory read/write"* (exit 11). A single
nested struct (`inner: Inner`) did not reproduce the crash; the nested *array* form does.

#### Simple `a := b` where `b` is a virtual reference

When a `&param` receives an object that implements `__Value` (rather than a `VarRef`), the
parameter becomes a *virtual reference* (`VAR_VIRTUAL_OBJ`) and reads go through the
object's `__Value` getter. `Var::UpdateVirtualObj` cleared the not-numeric attribute but
left `VAR_ATTRIB_UNINITIALIZED` set, so the optimised simple-assignment path
(`Line::PerformAssign`, used for `a := b` with no other operators) reported
*"This parameter has not been assigned a value"*. The attribute is now cleared.

```autohotkey
#Requires AutoHotkey v2.1-alpha.31
class Cell {
    __New(v) => this._v := v
    __Value {
        get => this._v
        set => this._v := value
    }
}
CopyOut(&src) {
    a := src               ; simple assignment — threw on alpha.30
    return a
}
c := Cell(42)
MsgBox(Type(CopyOut(c)))   ; => Cell   (see note)
x := 7
MsgBox(CopyOut(&x))        ; => 7      (VarRef — a genuine alias)
```

*Note:* on alpha.31 the simple form no longer throws, but for an object-backed reference it
copies the reference object itself (`Type(a)` is `Cell`) rather than reading `__Value`.
Any expression form — `a := src ?? 0`, `a := src + 0`, passing `src` as an argument — reads
the value `42`, on both alpha.30 and alpha.31. Treat the simple-assignment result as
unsettled and use an expression form when you need the value.

### GUI (not verifiable headless; paraphrased from the commits)

- **`GuiCtrl.OnMessage` threads no longer overrun `#MaxThreads`.** `GuiType::MsgMonitor`
  now returns without launching a thread when `g_nThreads >= g_MaxThreadsTotal`, so the
  message falls through to default processing instead of starting a thread beyond the
  limit.
- **`Thread "Priority", n` with `n > 0` now blocks `GuiCtrl.OnMessage` threads**, matching
  the rule that already applied to `OnMessage` callbacks and hotkeys: a message monitor
  cannot interrupt a thread whose priority is above zero.

### Via the v2.0 merge (v2.0.27, 28 Aug 2026)

The merge `Merge branch 'v2.0' into alpha` brings v2.0.27 to the alpha tree. Of its six
items, one (breakpoint on a `=>` line whose parent is a block) had already landed on the
alpha branch in alpha.30, and one (self-subclass check) was not merged as code because the
alpha branch already covers it — see its bullet. The remaining four are in the sources.

- **Setter definition permitted after a separate getter.** A second `prop { … }` block
  supplying only `set` was rejected with *"Duplicate declaration"* when a getter-only block
  came first, while the reverse order was accepted (due to a bug). Both orders are now
  allowed; `AddFunc` still rejects two getters or two setters. `Object::PropType` was
  simplified from `DynamicValue` / `DynamicMethod` / `DynamicMixed` to `Dynamic` /
  `DynamicWithMethod`.

  ```autohotkey
  class Cfg {
      Level {
          get => 42
      }
      Level {                ; alpha.30: "Duplicate declaration"
          set => this._log := "set " value
      }
  }
  c := Cfg()
  c.Level := 7
  MsgBox(c.Level " / " c._log)   ; => 42 / set 7
  ```

- **A class can no longer subclass itself.** On v2.0 this adds an *"Invalid base class."*
  check to `DefineClass` for the forward-reference path (a class object created as a
  placeholder because an earlier class extended it). **The alpha tree does not contain
  that code:** the merge commit changes nothing in `DefineClass`, and neither
  `Script::ClassResolutionError` nor the new check exists in the `v2.1-alpha.31` sources.
  The alpha branch resolves forward-referenced bases through its own
  `mUnresolvedBaseClass` pass in `PreparseVarRefs`, which already rejected self and cyclic
  bases, so `class B extends B {}` and `class A extends B {}` / `class B extends A {}`
  fail identically on alpha.30 and alpha.31.

  ```autohotkey
  class A extends B {
  }
  class B extends B {   ; => load error: Invalid base class.  Specifically: B
  }
  ```

- **`ContextMenu` event `Item` parameter from a ListView's header.** Right-clicking the
  header control of a ListView raises `ContextMenu` on the ListView; the `Item` parameter
  was computed from the header's notification structure as if it were a row click. The
  row index is now filled in only when the notification comes from the ListView itself.
  (Not verifiable headless.)
- **`IServiceProvider` interface pointer leak in `ComObjQuery`.** The three-parameter form
  (`ComObjQuery(obj, SID, IID)`) queried `IServiceProvider` and never released it. One
  `Release()` added. (Not verifiable from script.)
- **`Send "{Click X Y Count}"` moves once, not `Count` times.** The mouse was moved to
  `X, Y` on every repetition; the coordinates are now cleared after the first click so
  only the click repeats. (Not verifiable headless.)

## Internal / build changes

- `ACT_EXPORT` removed from `enum_act` and from `g_act[]`; `ACT_IS_VAR_DECL` range starts at
  `ACT_STATIC` again. `Script::IsFunctionDefinition`, `IsClassDefinition`,
  `Script::DefineClass` and `Script::AddFunc` lose their export/default-export parameters
  and branches (about 100 lines deleted and 35 added across `script.cpp`, `script.h`,
  `defines.h`, `globaldata.cpp` — net roughly −65).
- `VAR_EXPORTED` (0x80) renamed `VAR_IMPORTED` with inverted meaning; `Var::IsExported()`
  is `!(mScope & VAR_IMPORTED)`. `ScriptModule::AddNewImportVar` sets `VAR_IMPORTED` for
  non-`Export` imports. `FindOrAddBuiltInVar` and `Object::CreateClass` no longer set an
  export flag.
- `ScriptModule::FindImportedVar` rejects names beginning with `_` (wildcard privacy rule).
- `ScriptModule::mSelf` removed (`3574ce3c`); `Script::ResolveImports` passes `nullptr`
  as the alias target for `#Import X as Y`.
- `Script::LoadFromFile` temporarily links `mDefaultModule.mPrev` to `mBuiltinModule`
  around `ResolveImports()` (with `ASSERT`s guarding against a circular list);
  `FindModuleFileIndex` returns `CONDITION_FALSE` for an empty name when the current module
  has no file (`#Module AHK`).
- `IsFunctionDefinition`: leftover `!is_export` test removed (`3e955370`, "Fix obsolete
  expression").
- `MdFunc::Call`: `SYM_MISSING` from a `Variant` output parameter is converted to `""`
  before assignment (`9a8b1514` supersedes `7dbdf233`).
- `Object::PropEnum` gains `mMemToFree`; `BIF_Props` dereferences a `SYM_VAR` argument up
  front and duplicates string values.
- `Line::ExpandExpression` uses `IsUninitialized()` instead of `IsUninitializedAliasFor()`
  for imported vars; `Var::SelfInitialize` flattens multi-level aliases.
- `error_reporting_marker` for dynamic member calls: `cp - int(*(cp - 1) == g_DerefChar)`
  instead of the unconditional `cp - 1`.
- `Object::~Object` checks the vtable pointer of each nested slot before calling
  `~Object()`.
- `Var::UpdateVirtualObj` clears `VAR_ATTRIB_UNINITIALIZED` in addition to
  `VAR_ATTRIB_NOT_NUMERIC`.
- `GuiType::MsgMonitor` early-outs on `g_nThreads >= g_MaxThreadsTotal` and on
  `g->Priority > 0`.
- `Object::PropType` enum consolidated (`Dynamic`, `DynamicWithMethod`). The v2.0.27
  `Script::ClassResolutionError` / `DefineClass` self-subclass check was not merged into
  the alpha tree (already covered by `mUnresolvedBaseClass`).
- v2.0 merge (`54842af1`) touched `keyboard_mouse.cpp`, `script.cpp`, `script_com.cpp`,
  `script_gui.cpp`, `script_object.h` (28 insertions, 16 deletions).
