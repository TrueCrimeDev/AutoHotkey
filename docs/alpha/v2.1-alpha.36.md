# AutoHotkey v2.1-alpha.36

**Released:** 2026-10-18
**Previous:** [v2.1-alpha.35](./v2.1-alpha.35.md)
**Upstream tag:** [`v2.1-alpha.36`](https://github.com/AutoHotkey/AutoHotkey/tree/v2.1-alpha.36)

> Latest release in the v2.1-alpha series as of 2026-10-21. Merged into this fork on
> 2026-10-21 (branch `m1/upstream-alpha36`).

## Overview

Alpha.36 adds `ObjCreateWithDataPtr` and fixes three alpha-only problems: an
`AhkLibPath` directory ignored after a missing one, constructor calls such as
`RegExMatchInfo()` that built an unusable object, and `#Import` silently shadowed
by a local variable of the same name. Five upstream commits after `3a1291c6`.

## New

### `ObjCreateWithDataPtr(ClassObj, Address)`

Reference: [ObjCreateWithDataPtr](https://www.autohotkey.com/docs/alpha/lib/ObjCreateWithDataPtr.htm).

Creates an object derived from `ClassObj.Prototype` with an internal data
pointer set to `Address`. `ClassObj` must support direct construction; otherwise
it throws `Error` "Invalid class". For a class with typed properties, `Address`
must be 0 or a compatible memory address: an address below 65536 throws
`ValueError` (parameter #2), and an invalid non-zero address can crash the
program.

Unlike calling the class, it skips `__Init` and `__New`, so instance variable
initializers do not run. Unlike `StructClass.At`, it accepts Address 0 and calls
`__Delete` when the object is released. Read the pointer back with
`ObjGetDataPtr` (or `.Ptr` on a struct).

```autohotkey
buf := Buffer(8, 0)
v := ObjCreateWithDataPtr(Int32, buf.Ptr)
v.__Value := 7                 ; NumGet(buf, "Int") is now 7

class View {
    n : Int32                  ; a typed property on an ordinary class
    __Delete() => Print("released")
}
o := ObjCreateWithDataPtr(View, buf.Ptr)
Print(o.n)                     ; 7
```

## Fixes (alpha-only)

### `AhkLibPath` directory after a missing one

A directory listed in `AhkLibPath` (or the default list) was ignored when the
previous one did not exist (`abe3ff20`). The fork had already fixed this on
2026-10-12 with the same change; see
[`docs/upstream/alpha35-searchpath-last-dir.md`](../upstream/alpha35-searchpath-last-dir.md).
`g_script.mSearchPath` is now also freed after the script loads (`ee7f3514`);
it is rebuilt on demand.

### Invalid constructor calls

`RegExMatchInfo()`, `File()`, `Func()`, `BoundFunc()`, `Closure()` and
`Enumerator()`, called directly or through `(Object.Call)(Class)`, threw nothing
and returned a plain Object on the native prototype, which a native method would
then read past (`65189b9c`). A native class prototype no longer inherits
`Object`'s factory, so each call now throws `ValueError` "Invalid base.".

One side effect: `(Object.Call)(Struct)` now returns a `Struct` instead of
throwing "Invalid base.", because the `Struct` prototype records the same
factory as `Object`.

### `#Import` and a conflicting local

`#Import` inside a function now raises a load error when the function has a
non-static local, a parameter, or (with `as`) an alias target of the same name,
whether it is declared before or after the `#Import` (`0b8e6fa3`):
"This import declaration conflicts with an existing local variable." or
"... with an existing parameter.". Before, the local silently shadowed the
import.

## Fork notes

- **Upstream bug, fixed in this build (2026-10-21):** `Object::CreateStructPtr`
  (`source/script_object.cpp`) wrote `ObjCreateWithDataPtr`'s pointer at
  `sizeof(Object)`, but `ObjGetDataPtr`, `ObjSetDataPtr` and typed properties
  read it at the class's `object_size`. For `Map`, `Array`, `Buffer`,
  `ProcessPipe` and `JSON.Object` the pointer overwrote the object's own fields
  and the heap was corrupted (exit 127 on the official alpha.36 zip). The fork
  starts the suffix at `object_size`; `qa/tests/test_alpha36.ahk` section 3 pins
  it and `docs/upstream/alpha36-createstructptr-offset.md` holds the report.
- **Upstream regression, fixed in this build (2026-10-22):** the same
  `CreateStructPtr` change sets `CannotOwnProps` only when
  `obj->IsOfType(Object::sStructPrototype)`, which it tested before `SetBase`,
  so the flag was never set. Every struct view from `StructClass.At`, a
  `Pt.Ptr` dereference and `ObjCreateWithDataPtr` on a struct accepted own
  properties: `Pt.At(ptr).foo := 1` and `Int32.At(ptr).foo := 1` succeeded,
  where alpha.35 threw `PropertyError` "This value of type "Pt" has no property
  named "foo"." Same on the official alpha.36 zip; no memory damage seen. The
  fork runs the test after `SetBase` (`f24c23d1`), so they throw again, while
  `ObjCreateWithDataPtr` on `Map` or a script class still returns an object
  that can own properties. `qa/tests/test_alpha36.ahk` section 7 pins it;
  listed in the upstream report.
- One conflict, in `Script::GetSearchPath`: upstream's `abe3ff20` is the fork's
  `57bb8dcc` fix, so upstream's line was taken.
- The constructor fix closes the fork's "latent factory bug" open item (same
  class as the `JSON()` bug fixed in `7b1a23b6`). The fork's classes are
  unaffected: `JSON()` still throws the fork's `TypeError`, `(Object.Call)(JSON)`
  still throws "Invalid base.", and `ProcessPipe`, `SyntaxError` and `JSONError`
  construct as before.
- `ObjCreateWithDataPtr(ProcessPipe, 0)` and `ObjCreateWithDataPtr(JSON, 0)`
  create instances without running `__New`. Both are safe: an unstarted
  `ProcessPipe` reports "The process was not started." (`Send` gives `OSError`
  6), and the `JSON.Object` works as an empty one.
- The engine now identifies as `2.1-alpha.36+Console`. `Print`, `Eval`, `JSON`,
  `Inspect`, `ProcessPipe`, `Check` and `TSParse` are unchanged.
- Verified on the MSVC x64 build: console gate 17/17 suites, `tools/check_all.py`,
  and the new `qa/tests/test_alpha36.ahk` (51 asserts; on the build without the
  offset fix only its two section 3 asserts fail, and on `a41db9a1`, which has
  it, only the five struct asserts of section 7).
